# Threat Model — v0 (Milestone 0)

This document describes what is actually true of the implementation as
it exists at the end of Milestone 0 (work packages 1–16). It is not a
description of the eventual vision in `docs/adr/` — where the current
code falls short of an accepted ADR, that is stated here explicitly,
not smoothed over. Every claim below is checked against the current
source, not against what was originally planned. This document will
need revision as new capabilities, ports, and adapters are added; it
describes v0 only.

## Trust boundaries

Every value that crosses into a capability invocation carries a
`Provenance`: a `Trust` level and a `Classification`
(`domain/provenance.py`). Three trust levels exist:

- **`USER_DIRECT`** — typed by a human, directly, right now. Today
  this is the *only* trust level actually produced by any real call
  path: every CLI argument (`ping`'s absence of arguments, the music
  subcommand selection, `read`'s path argument) is wrapped via
  `Provenance.user()`.
- **`SYSTEM`** — produced by JARVIS's own internals. Defined and
  available (`Provenance.system()`), but nothing in the current
  codebase constructs it. No capability today produces a value on
  this trust level.
- **`UNTRUSTED_EXTERNAL`** — content originating outside the user's
  direct control (a web page, an email, a file whose provenance is
  unknown). Today this is produced in exactly one place: the
  *returned content* of `fs.read_file`, wrapped as
  `Provenance.external(source=<path>, classification=SENSITIVE)`
  (`kernel/files.py`). It has never yet been produced on an
  *invocation argument* — no current capability accepts an
  externally-sourced argument.

This last point matters for the tier ladder below: `evaluate()`'s
taint-escalation path (an `UNTRUSTED_EXTERNAL`-tainted argument bumps
the required tier by one step) is implemented and exercised by direct
domain-level tests, but has never yet fired from a real, end-to-end
capability invocation. The mechanism exists; nothing has triggered it
in practice yet.

## Classification

Four levels exist (`PUBLIC`/`PERSONAL`/`SENSITIVE`/`SECRET`). Today,
only two are ever actually assigned: `PUBLIC` (the implicit default via
`Provenance.user()`) and `SENSITIVE` (`fs.read_file`'s returned
content, per the reasoning in `kernel/files.py`'s own docstring — an
arbitrary local file's content is not assumed benign just because it's
local). No capability has ever produced a `PERSONAL` or `SECRET`
value. `SECRET`'s unconditional-deny-to-any-cloud-provider rule
(CLAUDE.md, ADR-0014) has never been exercised against a real value —
there is no cloud-routing code in this system yet at all.

## The tier ladder, and exactly what each tier checks

Four tiers, lowest restriction first: `ALLOW` → `CONFIRM` →
`MANUAL_ONLY` → `DENY`. `evaluate()` (`domain/policy.py`) is the sole
place this is decided:

- **`ALLOW`** — granted unconditionally. `context` is never read at
  all. Today: `ping` (`READ_LOCAL`) and `fs.read_file`
  (`EGRESS_LOCAL`).
- **`CONFIRM`** — granted if `physical_confirmation_available` **or**
  `remote_confirmation_available` (either channel suffices — an OR,
  not an AND). Today: `music.play`/`music.pause`/`music.next`/
  `music.previous` (`WRITE_LOCAL`).
- **`MANUAL_ONLY`** — granted only if `physical_confirmation_available`.
  `remote_confirmation_available` is deliberately never read for this
  tier, even if `True` — quoting `policy.py`'s own comment: *"per the
  M0 threat model, voice/remote confirmation is a convenience filter,
  never an authorization boundary (defeated by replay/cloning)."*
  **No capability registered today uses this tier.**
- **`DENY`** — an absolute ceiling; `granted` is always `False`,
  regardless of any confirmation. **No capability registered today
  uses this tier**, and taint-escalation has never pushed a real
  invocation here either (see above).

### The most important honesty point in this document

`ManualConfirmationAdapter` (`adapters/confirmation.py`) — the only
implementation of `ConfirmationPort` that exists — reports fixed,
**constructor-supplied** booleans. In the real CLI, those booleans come
directly from `--physical-confirmation-available` /
`--remote-confirmation-available` flags: plain, self-reported claims
typed by whoever is running the command, with **no presence sensor,
biometric check, hardware token, or any other real-world signal behind
them.**

Concretely: today, `CONFIRM` and `MANUAL_ONLY` provide *identical*
real-world protection, because both are satisfied by the same
unverified CLI flag — and no capability currently uses `MANUAL_ONLY`
anyway, so this hasn't yet been exercised even nominally. The tier
ladder is real, tested, and correctly enforced *given its inputs*; the
inputs themselves are not yet backed by anything a threat model can
credit as an authorization boundary. **A physical-presence-detection
adapter does not exist.** Anyone who can run the `jarvis` command with
normal user-level shell access can claim physical presence and have it
accepted at face value.

## `fs.read_file`'s path scope: a structural boundary, not a tier

`fs.read_file` is `ALLOW`-tier (see above) precisely because its real
protection is not the tier ladder at all: `kernel/files.py` resolves
every requested path (`expanduser().resolve()`, which follows symlinks
to their real target) and rejects it outright — before any
`CapabilityInvocation` is even constructed — if it falls outside
`allowed_root` (the real user's home directory, in production use).
No confirmation flag can override this. It is a single coarse
boundary (all of `$HOME`, not a denylist of sensitive subpaths like
`.ssh/`), deliberately: this project has consistently favored
allowlists over denylists (ADR-0007's spirit), and a denylist of
"known-sensitive" paths creates a false sense of completeness that a
coarse allowlist boundary does not.

## Known, explicitly-accepted gaps

Three gaps remain open and are stated here plainly, in decreasing
order of how directly they contradict something this project already
decided to do differently. They keep their original numbers (2–4)
rather than being renumbered after Gap 1 was closed, so that existing
references to a specific gap (`docs/plugin-guide/README.md`,
`docs/protocol/README.md`) stay accurate without needing to change in
lockstep with this document.

### Gap 1 (resolved, work package 18): the audit log used to store raw argument values, not digests

ADR-0027 decided: *"The audit log records only digests (hashes) of
capability invocation arguments, never the argument values
themselves."* CLAUDE.md repeats this as a hard privacy rule. From work
package 12 through work package 17, the actual implementation did not
do this: `adapters/audit_storage.py`'s `_encode_arguments()` wrote the
full, raw argument value directly into the persisted JSON audit file.
This was caught by this threat model (Milestone 0 closeout, work
package 17), not by any test, because no test at the time asserted the
*absence* of raw values from the persisted file — only that
round-tripping was correct.

Work package 18 fixed this at its root: `domain/audit.py`'s
`_canonicalize` — the same function that computes every
`AuditRecord.record_hash` — now treats a `Tainted` value as a special
case, reducing it to a sha256 digest of its `.value`
(`domain.audit.digest_value`) rather than walking into the value
itself. `adapters/audit_storage.py` persists that digest
(`"value_digest"`) instead of the raw value. Because the hash-chain's
own tamper detection is computed from the same canonical form the
persisted file is derived from, this is not merely "the file looks
safer" — a record whose persisted digest doesn't match what its
`record_hash` commits to is provably tampered, the same guarantee
every other field already had.

Two consequences, stated plainly:

- **This is a permanent, one-way change with no migration path.** A
  chain file written before work package 18 cannot be loaded by this
  or any later version: the raw argument values needed to recompute a
  valid digest under the new formula were never persisted, by design.
  Attempting to load one raises `KeyError` (missing `"value_digest"`),
  surfaced by the CLI as a clean `Error: ...` and exit `1`, not a raw
  traceback or a silent misparse.
- **Scope is argument *values* only.** `Provenance` (trust,
  classification, sources) attached to an argument is unaffected and
  still persists in full — ADR-0027 scopes the digest-only requirement
  to argument values, not their provenance metadata, and knowing an
  argument's trust/classification without its content is not the kind
  of exposure ADR-0027 was written to prevent.

The regression this gap was missing now exists:
`tests/unit/test_audit_storage_adapter.py::test_saved_file_never_contains_the_raw_argument_value`
asserts a marker string placed in an argument value never appears
anywhere in the persisted file's bytes, not just that round-tripping
happens to produce the right shape.

### Gap 2: no header/payload split, so nothing in the audit chain can ever be redacted

ADR-0028 decided audit entries would split into a header (hashed,
never redacted) and a payload (redactable independently, without
breaking the chain) — specifically to support cases like a
right-to-erasure request. The actual `AuditRecord`
(`domain/audit.py`) is flat: `sequence`, `decision`, `previous_hash`,
`record_hash`, with no header/payload distinction anywhere. Unlike Gap
1, this was never attempted, not contradicted — closer in kind to the
next gap. But the practical consequence is real: **there is currently
no way to redact anything from the audit chain without breaking
tamper-evidence for every record after it.**

### Gap 3: the hash chain detects tampering, but is not signed

Stated in `domain/audit.py`'s own module docstring since work package
5, quoted here rather than restated: *"this chain detects any
tampering with a single record, or any partial reordering that isn't
accompanied by recomputing every subsequent hash. It does NOT protect
against an attacker with write access to storage who is willing to
relabel sequence numbers and recompute hashes forward through the rest
of the chain — that requires a signing key, HMAC, or external
anchoring, none of which this module provides."*

### Gap 4: an out-of-scope file-read attempt leaves no audit record at all

Stated in `kernel/files.py`'s `PathOutsideAllowedScopeError` docstring
since work package 15, quoted here rather than restated: *"because
this rejection happens before any `CapabilityInvocation` is
constructed, out-of-scope access attempts are NOT recorded in the
audit chain — unlike a granted or normally-denied decision, there is
no forensic record of who tried to read what outside the allowed
root."* Closing this requires either extending `evaluate()`'s
escalation formula (a frozen work-package-4 change) or a separate,
out-of-band security-event log — neither exists yet.

## What is explicitly not yet defended against

Stated plainly, not implied:

- **No real physical-presence detection.** See "the most important
  honesty point" above — this is the single largest gap between what
  the tier ladder implies and what it currently delivers.
- **No plugin sandboxing.** `jarvis.plugin_api` has no real content
  yet. Nothing untrusted loads or executes in this system today —
  every capability is hardcoded in this same source tree
  (`kernel/capabilities.py`). The moment third-party plugin loading
  exists, this threat model will need a real section on it; today
  there is nothing to defend because there is no plugin loader.
- **No signed or externally-anchored audit chain** (Gap 3, above).
- **No encryption at rest for the audit log.** It is a plain JSON
  file, readable by anyone with filesystem access to it.
- **No atomic writes for the audit file.** `adapters/audit_storage.py`
  states this in its own docstring: a crash mid-`save()` can leave a
  partially-written file. Not handled.
- **No verification that a `ConfirmationPort` adapter is telling the
  truth.** Even a future, more sophisticated confirmation adapter is
  only as trustworthy as its own implementation; nothing in the
  policy engine cross-checks a confirmation signal against anything
  else.

## Summary

The policy engine, capability registry, and audit chain's internal
consistency (per-record tamper detection, hash linkage, and now,
digest-only argument logging) are real, tested, and enforced exactly
as designed. What is *not* yet real: any actual authorization signal
behind `CONFIRM`/`MANUAL_ONLY` beyond a self-reported CLI flag, any
capability dangerous enough to need `MANUAL_ONLY`, redaction (Gap 2),
chain signing (Gap 3), and plugin sandboxing. Milestone 0 built
the enforcement machinery honestly; it has not yet been asked to
enforce anything under real adversarial pressure, because nothing in
the current capability set is dangerous enough to test it, and the
one thing that would matter most under pressure — a real presence
signal — does not exist yet.
