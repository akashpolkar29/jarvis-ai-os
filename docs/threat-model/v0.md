# Threat Model — v0 (Milestone 0)

This document describes what is actually true of the implementation as
it exists at the end of Milestone 0 (work packages 1–16). It is not a
description of the eventual vision in `docs/adr/` — where the current
code falls short of an accepted ADR, that is stated here explicitly,
not smoothed over. Every claim below is checked against the current
source, not against what was originally planned. This document will
need revision as new capabilities, ports, and adapters are added; it
describes v0 only.

## Trust boundaries

Every value that crosses into a capability invocation carries a
`Provenance`: a `Trust` level and a `Classification`
(`domain/provenance.py`). Three trust levels exist:

- **`USER_DIRECT`** — typed by a human, directly, right now. Today
  this is the *only* trust level actually produced by any real call
  path: every CLI argument (`ping`'s absence of arguments, the music
  subcommand selection, `read`'s path argument) is wrapped via
  `Provenance.user()`.
- **`SYSTEM`** — produced by JARVIS's own internals. Defined and
  available (`Provenance.system()`), but nothing in the current
  codebase constructs it. No capability today produces a value on
  this trust level.
- **`UNTRUSTED_EXTERNAL`** — content originating outside the user's
  direct control (a web page, an email, a file whose provenance is
  unknown). Today this is produced in exactly one place: the
  *returned content* of `fs.read_file`, wrapped as
  `Provenance.external(source=<path>, classification=SENSITIVE)`
  (`kernel/files.py`). It has never yet been produced on an
  *invocation argument* — no current capability accepts an
  externally-sourced argument.

This last point matters for the tier ladder below: `evaluate()`'s
taint-escalation path (an `UNTRUSTED_EXTERNAL`-tainted argument bumps
the required tier by one step) is implemented and exercised by direct
domain-level tests, but has never yet fired from a real, end-to-end
capability invocation. The mechanism exists; nothing has triggered it
in practice yet.

## Classification

Four levels exist (`PUBLIC`/`PERSONAL`/`SENSITIVE`/`SECRET`). Today,
only two are ever actually assigned: `PUBLIC` (the implicit default via
`Provenance.user()`) and `SENSITIVE` (`fs.read_file`'s returned
content, per the reasoning in `kernel/files.py`'s own docstring — an
arbitrary local file's content is not assumed benign just because it's
local). No capability has ever produced a `PERSONAL` or `SECRET`
value. `SECRET`'s unconditional-deny-to-any-cloud-provider rule
(CLAUDE.md, ADR-0014) has never been exercised against a real value —
there is no cloud-routing code in this system yet at all.

## The tier ladder, and exactly what each tier checks

Four tiers, lowest restriction first: `ALLOW` → `CONFIRM` →
`MANUAL_ONLY` → `DENY`. `evaluate()` (`domain/policy.py`) is the sole
place this is decided:

- **`ALLOW`** — granted unconditionally. `context` is never read at
  all. Today: `ping` (`READ_LOCAL`) and `fs.read_file`
  (`EGRESS_LOCAL`).
- **`CONFIRM`** — granted if `physical_confirmation_available` **or**
  `remote_confirmation_available` (either channel suffices — an OR,
  not an AND). Today: `music.play`/`music.pause`/`music.next`/
  `music.previous` (`WRITE_LOCAL`).
- **`MANUAL_ONLY`** — granted only if `physical_confirmation_available`.
  `remote_confirmation_available` is deliberately never read for this
  tier, even if `True` — quoting `policy.py`'s own comment: *"per the
  M0 threat model, voice/remote confirmation is a convenience filter,
  never an authorization boundary (defeated by replay/cloning)."*
  **No capability registered today uses this tier.**
- **`DENY`** — an absolute ceiling; `granted` is always `False`,
  regardless of any confirmation. **No capability registered today
  uses this tier**, and taint-escalation has never pushed a real
  invocation here either (see above).

### The most important honesty point in this document

`ManualConfirmationAdapter` (`adapters/confirmation.py`) — the only
implementation of `ConfirmationPort` that exists — reports fixed,
**constructor-supplied** booleans. In the real CLI, those booleans come
directly from `--physical-confirmation-available` /
`--remote-confirmation-available` flags: plain, self-reported claims
typed by whoever is running the command, with **no presence sensor,
biometric check, hardware token, or any other real-world signal behind
them.**

Concretely: today, `CONFIRM` and `MANUAL_ONLY` provide *identical*
real-world protection, because both are satisfied by the same
unverified CLI flag — and no capability currently uses `MANUAL_ONLY`
anyway, so this hasn't yet been exercised even nominally. The tier
ladder is real, tested, and correctly enforced *given its inputs*; the
inputs themselves are not yet backed by anything a threat model can
credit as an authorization boundary. **A physical-presence-detection
adapter does not exist.** Anyone who can run the `jarvis` command with
normal user-level shell access can claim physical presence and have it
accepted at face value.

## `fs.read_file`'s path scope: a structural boundary, not a tier

`fs.read_file` is `ALLOW`-tier (see above) precisely because its real
protection is not the tier ladder at all: `kernel/files.py` resolves
every requested path (`expanduser().resolve()`, which follows symlinks
to their real target) and rejects it outright — before any
`CapabilityInvocation` is even constructed — if it falls outside
`allowed_root` (the real user's home directory, in production use).
No confirmation flag can override this. It is a single coarse
boundary (all of `$HOME`, not a denylist of sensitive subpaths like
`.ssh/`), deliberately: this project has consistently favored
allowlists over denylists (ADR-0007's spirit), and a denylist of
"known-sensitive" paths creates a false sense of completeness that a
coarse allowlist boundary does not.

## Known, explicitly-accepted gaps

Three gaps remain open and are stated here plainly, in decreasing
order of how directly they contradict something this project already
decided to do differently. They keep their original numbers (2–4)
rather than being renumbered after Gap 1 was closed, so that existing
references to a specific gap (`docs/plugin-guide/README.md`,
`docs/protocol/README.md`) stay accurate without needing to change in
lockstep with this document.

### Gap 1 (resolved, work package 18): the audit log used to store raw argument values, not digests

ADR-0027 decided: *"The audit log records only digests (hashes) of
capability invocation arguments, never the argument values
themselves."* CLAUDE.md repeats this as a hard privacy rule. From work
package 12 through work package 17, the actual implementation did not
do this: `adapters/audit_storage.py`'s `_encode_arguments()` wrote the
full, raw argument value directly into the persisted JSON audit file.
This was caught by this threat model (Milestone 0 closeout, work
package 17), not by any test, because no test at the time asserted the
*absence* of raw values from the persisted file — only that
round-tripping was correct.

Work package 18 fixed this at its root: `domain/audit.py`'s
`_canonicalize` — the same function that computes every
`AuditRecord.record_hash` — now treats a `Tainted` value as a special
case, reducing it to a sha256 digest of its `.value`
(`domain.audit.digest_value`) rather than walking into the value
itself. `adapters/audit_storage.py` persists that digest
(`"value_digest"`) instead of the raw value. Because the hash-chain's
own tamper detection is computed from the same canonical form the
persisted file is derived from, this is not merely "the file looks
safer" — a record whose persisted digest doesn't match what its
`record_hash` commits to is provably tampered, the same guarantee
every other field already had.

Two consequences, stated plainly:

- **This is a permanent, one-way change with no migration path.** A
  chain file written before work package 18 cannot be loaded by this
  or any later version: the raw argument values needed to recompute a
  valid digest under the new formula were never persisted, by design.
  Attempting to load one raises `KeyError` (missing `"value_digest"`),
  surfaced by the CLI as a clean `Error: ...` and exit `1`, not a raw
  traceback or a silent misparse.
- **Scope is argument *values* only.** `Provenance` (trust,
  classification, sources) attached to an argument is unaffected and
  still persists in full — ADR-0027 scopes the digest-only requirement
  to argument values, not their provenance metadata, and knowing an
  argument's trust/classification without its content is not the kind
  of exposure ADR-0027 was written to prevent.

The regression this gap was missing now exists:
`tests/unit/test_audit_storage_adapter.py::test_saved_file_never_contains_the_raw_argument_value`
asserts a marker string placed in an argument value never appears
anywhere in the persisted file's bytes, not just that round-tripping
happens to produce the right shape.

### Gap 2: no header/payload split, so nothing in the audit chain can ever be redacted

ADR-0028 decided audit entries would split into a header (hashed,
never redacted) and a payload (redactable independently, without
breaking the chain) — specifically to support cases like a
right-to-erasure request. The actual `AuditRecord`
(`domain/audit.py`) is flat: `sequence`, `decision`, `previous_hash`,
`record_hash`, with no header/payload distinction anywhere. Unlike Gap
1, this was never attempted, not contradicted — closer in kind to the
next gap. But the practical consequence is real: **there is currently
no way to redact anything from the audit chain without breaking
tamper-evidence for every record after it.**

### Gap 3: the hash chain detects tampering, but is not signed

Stated in `domain/audit.py`'s own module docstring since work package
5, quoted here rather than restated: *"this chain detects any
tampering with a single record, or any partial reordering that isn't
accompanied by recomputing every subsequent hash. It does NOT protect
against an attacker with write access to storage who is willing to
relabel sequence numbers and recompute hashes forward through the rest
of the chain — that requires a signing key, HMAC, or external
anchoring, none of which this module provides."*

### Gap 4: an out-of-scope file-read attempt leaves no audit record at all

Stated in `kernel/files.py`'s `PathOutsideAllowedScopeError` docstring
since work package 15, quoted here rather than restated: *"because
this rejection happens before any `CapabilityInvocation` is
constructed, out-of-scope access attempts are NOT recorded in the
audit chain — unlike a granted or normally-denied decision, there is
no forensic record of who tried to read what outside the allowed
root."* Closing this requires either extending `evaluate()`'s
escalation formula (a frozen work-package-4 change) or a separate,
out-of-band security-event log — neither exists yet.

## What is explicitly not yet defended against

Stated plainly, not implied:

- **No real physical-presence detection for direct CLI invocation.**
  See "the most important honesty point" above — still true exactly as
  written for `jarvis ping`/`play`/`pause`/`next`/`previous`/`read`'s
  `--physical-confirmation-available` flag, which remains a plain,
  self-reported claim. As of Milestone 1, this is **no longer true for
  voice-triggered invocation** (`jarvis listen`) — see "Milestone 1
  additions" below for the real, physical-keypress mechanism that path
  now goes through instead. The gap this bullet originally described
  has narrowed, not closed: it is now specific to the CLI's own flags,
  not the whole system.
- **No plugin sandboxing.** `jarvis.plugin_api` has no real content
  yet. Nothing untrusted loads or executes in this system today —
  every capability is hardcoded in this same source tree
  (`kernel/capabilities.py`). The moment third-party plugin loading
  exists, this threat model will need a real section on it; today
  there is nothing to defend because there is no plugin loader.
- **No signed or externally-anchored audit chain** (Gap 3, above).
- **No encryption at rest for the audit log.** It is a plain JSON
  file, readable by anyone with filesystem access to it.
- **No atomic writes for the audit file.** `adapters/audit_storage.py`
  states this in its own docstring: a crash mid-`save()` can leave a
  partially-written file. Not handled.
- **No verification that a `ConfirmationPort` adapter is telling the
  truth.** Even a future, more sophisticated confirmation adapter is
  only as trustworthy as its own implementation; nothing in the
  policy engine cross-checks a confirmation signal against anything
  else.

## Summary

The policy engine, capability registry, and audit chain's internal
consistency (per-record tamper detection, hash linkage, and now,
digest-only argument logging) are real, tested, and enforced exactly
as designed. What is *not* yet real: any actual authorization signal
behind `CONFIRM`/`MANUAL_ONLY` beyond a self-reported CLI flag, any
capability dangerous enough to need `MANUAL_ONLY`, redaction (Gap 2),
chain signing (Gap 3), and plugin sandboxing. Milestone 0 built
the enforcement machinery honestly; it has not yet been asked to
enforce anything under real adversarial pressure, because nothing in
the current capability set is dangerous enough to test it, and the
one thing that would matter most under pressure — a real presence
signal — does not exist yet.

## Milestone 1 additions

Appended per `docs/architecture/m1-voice-architecture.md` section 5,
with real content reflecting what was actually built (work packages
19–26), not the placeholder text that section originally sketched.
Everything above this heading describes Milestone 0 exactly as it was

new facts are added here, not blended backward into the M0 snapshot.

### Always-on listening is a new, permanent privacy surface

Wake-word detection (`OpenWakeWordAdapter`, WP-20) runs continuously
on-device for as long as `jarvis listen` is running. It must never
touch the network — openWakeWord's tflite inference path is fully
local — and the ring buffer feeding it (`_AudioRingBuffer`) must never
be written to disk under any circumstance. This extends ADR-0018 ("no
audio persisted to disk") from "no audio persisted" to "no audio
persisted, including transiently during wake-word evaluation itself" —
checked directly: `_AudioRingBuffer` is a plain in-memory `deque`, with
no file I/O anywhere in its implementation, and this is exercised by
`tests/unit/test_wake_word_adapter.py`'s ring-buffer tests.

**A legal note, carried forward from the original M0 review, that
still applies and has not been re-derived:** recording someone else's
non-public spoken word without consent is treated seriously under
German law (§201 StGB). A household microphone that can capture
flatmates or visitors is exactly the situation that contemplates. The
ring-buffer-only, never-persisted design is a direct mitigation, not a
complete one — it limits what could ever be exfiltrated or recovered
after the fact, but does not by itself address consent for people
other than the primary user who happen to be audible to an always-on
microphone. This remains open, stated plainly rather than assumed
solved.

### Finding 2 is closed for voice-triggered invocation, not for the CLI's own flags

See ADR-0035 for the full design and the two real implementation bugs
manual verification caught. The claim, stated precisely: **as of
`PhysicalConfirmationPort`/`Gtk4PhysicalConfirmationAdapter` (WP-24)
and `kernel.voice_loop.run_voice_loop` (WP-25), any command resolved
from voice input requires a physical keypress or click — on a
GTK4 dialog whose Approve/Deny handlers verify a genuine `Gdk.Event`
backed by a real input device — that voice alone cannot produce.**
`tests/unit/test_confirmation_dialog.py` proves the underlying check
rejects a fabricated or missing event, closing the specific gap the
M1 doc named: *"this needs its own test proving a simulated or
injected keypress event is rejected the same way M0's original
synthetic-input interlock was designed to prevent"* — no such interlock
actually existed in M0 (checked directly: no synthetic-input handling
of any kind appears anywhere in the M0 source), so this test is the
first one, not a continuation of a prior mechanism.

This closure is intentionally narrow, matching what was actually
built rather than overclaiming: it applies to the `jarvis listen` path
specifically. `jarvis ping`/`play`/`pause`/`next`/`previous`/`read`'s
`--physical-confirmation-available` flag is completely unchanged —
still a self-reported CLI boolean, per "the most important honesty
point" above. `ManualConfirmationAdapter` was not modified, deprecated,
or replaced; it remains in normal use for every non-voice invocation,
per the M1 architecture doc's own recommendation (section 11, open
question 3) to run the two paths alongside each other rather than
unify them.

Scope, stated as honestly here as in ADR-0035 itself: the physical-
keypress mechanism defends against software-only confirmation forgery
(an in-process call faking a click, a voice recording, a network-
triggered invocation with no human at the keyboard at all) — it is not
claimed to defend against an attacker who already has root or
`/dev/uinput` access on the machine, a strictly stronger capability
than any of those. `MANUAL_ONLY` is still not bulletproof against an
attacker with full control of the session; it is now, for the first
time, backed by something voice/recording/remote access genuinely
cannot satisfy on its own.

### Speaker verification remains audit/UX only, now mechanically enforced

See ADR-0034. `SpeakerIdPort`/`UnverifiedSpeakerIdAdapter` (WP-23)
exist and are wired into `kernel.voice_loop.run_voice_loop`, but their
output is logged only — never read again, never used to construct a
`PolicyContext`. `tests/meta/test_speaker_id_isolation.py` verifies
this holds structurally across the whole `src/jarvis` tree, not just
by convention.

### A real, previously-undisclosed drift found and corrected during Track 6's full-repo health pass (2026-09-02): the `v0.2.0` tag's own exact commit was tagged while CI was genuinely red, not green

Found by walking every tag's own real commit SHA (careful to dereference
`v0.2.0` as an *annotated* tag object to its underlying commit, not the
tag object's own SHA, which `git rev-parse v0.2.0` alone returns and
which never matches any GitHub Actions `head_sha`) against the real
GitHub Actions run history via the API, not assumed from the tag's own
existence. Every tag from `v0.1.0` through `v0.5.0` checked this way;
five of six show a real, matching `conclusion: success` run against
their exact tagged commit. `v0.2.0` (M1's tag, commit `08f13f2`, tagged
2026-08-15) does not: its one and only real CI run
(`actions/runs/31899647509`) shows `conclusion: failure`, both matrix
jobs (`py3.12`, `py3.13`) failing at the `Install dependencies` step —
before any gate ever ran. The next commit on `main` after the tag
(`6dabb43`, 2026-08-17) failed the identical way. This was not a new
discovery in the sense of "no one ever noticed" — commit `8c1c6cef`
(2026-08-18, `ci: install system deps for pygobject's build, fixing CI
since WP-24 (8ffad01)`) already root-caused and fixed the underlying
break: `pygobject` (introduced by WP-24, `8ffad01`) ships no prebuilt
wheel, and the CI workflow had no system-package install step for its
build dependencies until that commit. What *was* newly found here is
narrower and more specific: this project's own docs never disclosed
that the fix landed **three days after `v0.2.0` was already tagged**,
meaning the exact commit the tag points to never itself had a passing
CI run, and `CLAUDE.md`'s/`docs/ROADMAP.md`'s own "all 7 gates pass, CI
green" language for M1 was true of `main`'s state days later, not of
the tagged commit specifically — a real, if narrow, overstatement,
corrected in both files by this same pass rather than left standing.
No code change follows from this: `main`'s tip has been green on every
push since `8c1c6cef`, `v0.2.0`'s own tree was never functionally
broken (the failure was 100% a CI-configuration gap, not a test/gate
failure), and retagging or moving an already-published tag is exactly
the kind of destructive, hard-to-reverse action this project's own
git discipline avoids without the user's explicit direction — the tag
stays where it is, the record is corrected instead.

## Milestone 2 additions

Appended per the same convention `docs/architecture/m1-voice-architecture.md`

### Cloud egress to a reasoning provider is real for the first time

Milestone 0's `_EFFECT_TIER_FLOOR` already defined `EGRESS_SENSITIVE`/
`EGRESS_SECRET`, but "the current capability set" the M0 Summary above
names had nothing that declared either effect — checked directly at
the time (`kernel/capabilities.py`'s `build_default_registry()`
registered only `READ_LOCAL`/`WRITE_LOCAL`/`EGRESS_LOCAL`). `ModelRouter`
(WP-36) is the first real code that constructs a `CapabilityInvocation`
declaring `EGRESS_SENSITIVE` or `EGRESS_SECRET`, so ADR-0014/ADR-0015/
ADR-0038's Classification-based gating is exercised by real code,
through the real `AuthorizationOrchestrator`/`AuditChain` choke point
(ADR-0039), for the first time in this project's history — not merely
tested at the domain level in isolation, as it was after WP-30.

Recovered acceptance criterion #6 ("A SENSITIVE-classified task never
reaches a cloud provider at any rung") contradicted real, Accepted
ADR-0015 ("SENSITIVE data may be sent... behind an explicit CONFIRM").
Flagged during WP-36, resolved in ADR-0015's favor, not silently: a
SENSITIVE task can reach a cloud provider, but never without a real
confirmation channel present, and never by default —
`tests/property/test_router.py` asserts both halves of that claim
directly, not just the "never reaches" half the recovered wording
implied.

### A real, explicitly-accepted gap: candidate execution is not sandboxed

`WorkspacePort`/`LocalWorkspaceAdapter` (ADR-0043, WP-33) apply a
Candidate's content as a patch to real files on disk via `git apply`;
`RuntimeCheckValidator`, `PytestValidator`, and `UserScriptValidator`
then run real, caller-supplied commands against that patched workspace
via a plain subprocess, with the same privileges as the JARVIS process
itself — no container, no restricted user, no filesystem or network
limits, no resource caps. `FamilyAReasoningAdapter`/`FamilyBReasoningAdapter`
tag their output `Trust.UNTRUSTED_EXTERNAL` (WP-32) specifically
because a cloud provider's content is adversarially-manipulable, and a
validator that executes an `UNTRUSTED_EXTERNAL`-tainted Candidate's
content is, structurally, running attacker-influenceable code with
full process privileges the moment that candidate reaches a
`RuntimeCheckValidator`/`PytestValidator`/`UserScriptValidator` stage.

This is real, not hypothetical, and not fixed in M2: nothing in
`adapters/validation/` restricts what a patched workspace's code can
do once a validator's command is invoked. It is the same class of gap
deliverable #9 ("test-file protection in a coding agent's resource
scope") was meant to narrow, but broader — deliverable #9 itself
remains explicitly deferred to M5 (confirmed: no work package from
WP-32 through WP-40 restricts which files a Candidate's patch or a
validator's command may touch), and no sandboxing of any kind was
ever in this milestone's scope. Stated here rather than left implicit,
matching Gap 2–4's own precedent above: known, real, unresolved.

### Cassette files are plaintext, unencrypted regression fixtures

`CassetteRecorder`/`CassettePlayer` (ADR unrecorded as its own number —
see WP-38) write a real Candidate's full content, author, and
provenance to a plain JSON file under `tests/cassettes/`, with no
encryption, redaction, or access control. Recording a cassette from a
real task whose content happens to be `SENSITIVE`- or `SECRET`-classified
would permanently place that content in plaintext as a checked-in test
fixture. This is an operational discipline this milestone states but
does not mechanically enforce — no code in `CassetteRecorder` inspects
or gates on the wrapped provider's real output provenance before
writing it to disk. Nothing in this repository's real, checked-in
`tests/cassettes/` files carries any classification above `PUBLIC`
today; keeping it that way is a human discipline, not a checked
invariant.

The work-package plan this milestone followed named "acceptance

Checked directly against every real ADR in `docs/adr/`: only #9
(ADR-0038, SECRET never egresses) and #11 (ADR-0039, no vendor name

work-package orchestration text outside this repository's own history
— not in any ADR, not in `m2-reasoning-layer.md`, not anywhere

### Live verification of the reasoning adapters — tracked item, mirroring M1's #19

M2's closeout above flagged all three `ReasoningPort` adapters as
code-complete but never live-verified against a real provider. A
consolidation pass (post-`v0.3.0`) closed part of this gap for real,
one adapter at a time, and found the rest genuinely blocked rather
than silently left as before:

- **`local`**: fully live-verified. A real Ollama server (installed
  for this purpose, `llama3.2:1b` pulled) answered a real
  `LocalReasoningAdapter.generate()` call end to end — request shape,
  response-parsing shape, `Trust.SYSTEM` tagging, and the real
  `ModelRouter` → `AuthorizationOrchestrator` → `AuditChain` path (one
  real, hash-chained audit record produced) all confirmed correct
  against a live, real service. Confirmed absent, separately: no
  WP-28 PoC script was ever written or run, for any of the three
  adapters — checked directly against `poc/` and `git log`, not
  assumed.
- **`family_a`**: partially live-verified. `_ENDPOINT` was corrected
  from a deliberate `.example` placeholder (WP-32) to the real OpenAI
  Chat Completions host, and one real round-trip was attempted through
  the actual, unmodified `FamilyAReasoningAdapter`, with a real
  credential resolved via `SecretPort` (provisioned directly into the
  keyring by the user; never seen or handled as text by the assistant
  at any point). The request reached OpenAI and authenticated
  successfully — real evidence for the request shape (auth header,
  JSON body, `model`/`messages` fields) — but returned
  `insufficient_quota` (an account billing condition, not a shape
  error) before any response body existed to parse.
  `_extract_content`'s response-parsing shape remains genuinely
  unverified. The user explicitly declined to add API billing to
  resolve this, and separately asked whether the existing ChatGPT/Claude
  Pro web or desktop apps could be automated instead of the API —
  declined: that would be a new adapter (browser/app automation is a
  different integration entirely from an HTTP client), not a
  verification of this one, and automating a consumer subscription
  product outside its official API is very likely a Terms-of-Service
  violation for the user's account, not a design or scope choice this
  project should make on their behalf.
- **`family_b`**: not live-verified at all, by explicit, deliberate
  choice — no Anthropic credential was ever provisioned. Unit- and
  cassette-tested only.

None of this is treated as blocking: `v0.3.0` already shipped with
this gap honestly flagged, and this pass narrowed it rather than
being required to close it completely.

### Real sandboxing exists for the first time, but M2's own gap is not retrofitted

`SandboxPort`/`BwrapSandboxAdapter` (ADR-0044, WP-45) is this
project's first real, kernel-enforced containment mechanism —
genuinely verified live (not merely documented) during WP-45's own
test suite: a real `bwrap --unshare-all` sandbox denies outbound
network and denies filesystem access outside explicitly bound paths,
and an explicitly bound path is genuinely writable. This is exactly
the mechanism the "candidate execution is not sandboxed" gap (Milestone
2 additions, above) named as missing.

**Explicitly not retrofitted onto M2's validators**, decided before
this milestone's implementation began (`m3-desktop-control.md`'s
"Relationship to M2" section, ADR-0044's own "Consequences"):
`RuntimeCheckValidator`/`PytestValidator`/`UserScriptValidator` still
run real, caller-supplied commands with full JARVIS-process privileges
against `Trust.UNTRUSTED_EXTERNAL`-tagged cloud-provider content — the
exact same real, unresolved gap Milestone 2's own closeout already
named. `SandboxPort` is real, general-purpose infrastructure a future
work package *could* apply there; this milestone deliberately did not,
to stay scoped to desktop control rather than quietly expanding into
"M2 hardening." Stated here plainly: this gap is now *closeable* with
existing infrastructure, but is not yet closed.

### Terminal: a real, narrow, structurally-bounded exception to "no shell"

`terminal.run` (ADR-0046, WP-52) is the first capability in this
project's history whose whole purpose is accepting free-text input and
having it interpreted as a shell command — a deliberate, explicitly
argued exception to ADR-0003/ADR-0007, not a quiet erosion of them.
Three real, tested mitigations bound it: unconditional
`Tier.MANUAL_ONLY` (no `CONFIRM`-tier fast path, ever), a structural
guarantee that keystroke injection can only ever reach a terminal
window `SandboxPort` itself just launched (verified by AST scan,
`tests/meta/test_terminal_sandboxed_launch_only.py`, including a
self-test that the scan genuinely fires on a deliberate violation),
and unconditional `Trust.UNTRUSTED_EXTERNAL` tagging of any captured
output. **Never exercised against a real, visible terminal window
during this pass** — see "What was never live-verified" below.

### A new class of untrusted content: real desktop-application window state

`DesktopWindowPort.read_visible_text` (WP-44) introduces a genuinely
new source of `Trust.UNTRUSTED_EXTERNAL` content beyond M2's
cloud-provider responses: whatever text a real, running application's
own accessibility tree happens to expose. ADR-0011 already named this
class of content in the abstract ("a web page, a terminal's own
command output, an accessibility tree populated by an application this
process does not control"); this milestone is the first to build a
real port that can actually produce it. Real, live-confirmed during
WP-43's spike: AT-SPI2 access is not just gated by the *target*
application's own policy but by the *caller's* — a real `GetItems` call
against Brave's accessible tree, issued from this session's own
snap-confined shell, was denied by the snap D-Bus proxy independent of
any AppArmor policy on Brave itself. Whether a real, eventually-packaged
JARVIS process is itself snap-confined when this code actually runs
was not something this pass could control or verify in advance —
flagged as a real, environment-dependent risk, not assumed away.

### A real C6 layering violation, caught by the gate itself and fixed, not silently avoided

During WP-51, importing `AtspiDesktopWindowAdapter` directly into
`kernel/desktop.py` (to give `authorize_and_send_text_to_chat_app` a
real default, matching every sibling function's own shape) broke C6
("no GLib in the core") for real: `lint-imports` reported the genuine
transitive chain `jarvis.kernel.desktop -> jarvis.adapters.desktop_window
-> gi`. Fixed by making `desktop_window` (and, from WP-52 onward,
`sandbox`) required parameters with no default — mirroring
`kernel/voice_loop.py`'s own, already-established precedent for
`Gtk4PhysicalConfirmationAdapter` exactly. Recorded here because it is
a real, load-bearing example of this project's own gates catching a
genuine mistake mid-implementation, not a hypothetical the design docs
merely warned about.

### What was never live-verified — mirroring M1's #19 and M2's own closeout precedent

Every desktop-control capability this milestone built is
code-complete, gate-passing, and unit-tested against injected fakes —

  chose AT-SPI2's `EditableText`/`Component` interfaces instead,
  partly because calling `RemoteDesktop.CreateSession` for real would
  have popped a real system permission dialog on the user's live
  screen during an unattended run. Whether AT-SPI2 alone proves
  sufficient for every real target application (especially Electron-
  based ones, which have historically inconsistent AT-SPI2 support)
  is genuinely unconfirmed.
- **`gnome-terminal`'s own AT-SPI2 `Text` interface support is
  unconfirmed** — chosen over Brave/VS Code specifically because it is
  a native, non-snap binary (avoiding the D-Bus-proxy denial class
  above), but whether it actually exposes readable terminal content via

  unconfirmed.** WP-43's spike found a real, installed `claude-desktop`

  restriction than this run's own hard-stop rule strictly required
  (which named only `run`/`build` explicitly), applied for consistency
  and because this run had no way to confirm any given Docker
  environment was genuinely disposable. Live verification is deferred
  to when the user is present to supervise it directly, the same
  deferral shape M2's `family_a`/`family_b` live-verification gap used.
- **`git.push`/`git.force_push` were verified for real, but only
  against disposable local repositories** (`tests/unit/adapters/test_git.py`
  creates a fresh scratch working repo and a fresh local bare "remote"
  per test) — never against any real, network-reachable remote. A real
  fast-forward rejection and a real force-overwrite were both observed
  against real git subprocess behavior, which is more verification than
  Docker's capabilities received, but still zero verification against
  a real hosted remote (GitHub or otherwise).
- ~~`BwrapSandboxAdapter`'s CI behavior on a real GitHub-hosted runner is
  unconfirmed~~ **resolved, post-WP-55**: it was not just unconfirmed but
  genuinely broken on `ubuntu-latest` — every WP-45+ CI run failed for
  real, with `bwrap: loopback: Failed RTM_NEWADDR: Operation not
  permitted`. Root cause, confirmed against the real runner: `bwrap`
  successfully creates its unprivileged user+network namespace (Ubuntu's
  `bubblewrap` AppArmor profile does permit that), but the netlink call
  it then makes to bring up the sandbox's own loopback interface is
  denied — `ubuntu-latest`'s `kernel.apparmor_restrict_unprivileged_userns=1`
  default blocks `CAP_NET_ADMIN` inside the new namespace regardless of
  the profile permitting the namespace's own creation, a known, widely-
  reported issue affecting other bwrap-based sandboxes on GitHub-hosted
  runners generally, not specific to this adapter. Fixed in
  `.github/workflows/ci.yml` with one added step
  (`sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`,
  scoped to the ephemeral runner VM's own lifetime, touching nothing the
  sandbox itself contains once created) and verified live: every
  `BwrapSandboxAdapter` test — real network denial, real filesystem
  denial, real bind-path writes, real exit-code capture, real
  non-blocking `launch()` — passes for real on a real `ubuntu-latest`
  runner, both Python matrix legs, not skipped or weakened.
- **No numeric resource limits** (CPU/memory/pid caps) exist on any
  `SandboxPort`-contained process beyond filesystem/network isolation
  — a sandboxed command can still exhaust host CPU/memory/disk. Named
  as a real, unaddressed gap in ADR-0044 itself, restated here.

None of this is treated as blocking: this milestone's own acceptance
criteria (`m3-desktop-control.md`) already anticipated most of these
as open questions rather than promises, and this closeout records what
was actually found rather than rounding any of it up to "verified."

### A real, previously-undiscovered bug: SandboxPort.launch() could not display anything

`BwrapSandboxAdapter.launch()` never bound anything under `/run`, so
no GUI application launched through it could connect to the display
server at all -- confirmed live: a real, sandboxed `gnome-terminal`
failed immediately with `Cannot open display:`. This was a real,
shipped bug in WP-52's own Terminal capability, not merely an
unverified claim: **Terminal could not have displayed a real window
even once the WP-45+ CI fix landed.**

Root-caused live, including ruling out a false lead: an early test
appeared to show `--unshare-net` itself breaking Wayland access, which
would have been a genuine, hard architectural tension (the network
isolation Terminal's sandbox most needs colliding with its ability to
display anything at all, forcing a choice between ADR-0044's isolation
guarantee and ADR-0046's terminal-must-work requirement). Retested with
a genuinely clean environment and this was **not confirmed** -- the
original test's own shell (this verification session's own snap-
confined VS Code terminal) was polluting `GTK_PATH`/`GIO_MODULE_DIR`/
`LOCPATH` with paths that don't exist inside the sandbox, producing a
misleading symptom. With a clean environment, full `--unshare-all`
(network included) launches a real GUI application successfully once
the right sockets are bound. Real fix landed:
`_display_bind_paths()` (`adapters/sandbox.py`) binds the real Wayland
socket (`$XDG_RUNTIME_DIR/$WAYLAND_DISPLAY`) and D-Bus session socket
(`$XDG_RUNTIME_DIR/bus`) when `SandboxPort.launch(..., allow_display=
True)` is set; `run_in_sandboxed_terminal` now passes it. Verified
live: a real sandboxed `gnome-terminal` genuinely displays and runs a
real inner command (`tests/unit/adapters/test_sandbox.py::
test_launch_with_allow_display_can_really_display_a_real_gui_app`,
skipped on headless CI with a named reason, not weakened). X11 (as
opposed to Wayland) was not covered -- no real X11 session was
available to test against on this machine.

### A real, structural gap: Terminal's own type_text mechanism cannot type into a real terminal

With display now working, checked the VTE terminal widget's real
AT-SPI2 interfaces directly: it exposes `Text` (read works -- output
capture is genuinely possible) but **not `EditableText`**.
`AtspiDesktopWindowAdapter.type_text()`'s only mechanism is finding a
focused `EditableText` node and calling `insert_text` on it -- which
means **`terminal.run`'s real flow, as shipped, cannot type a command
into a real terminal at all**, the one app this capability exists for.
This is a genuine, structural limitation of the AT-SPI2-only mechanism
WP-43 chose (over the original "portal + libei" objective, set aside
because libei's GI binding was absent) -- terminals are not
conventional text-entry widgets and were never going to expose
`EditableText`. A real fix needs synthetic keyboard input (the
RemoteDesktop portal, or libei once packaged), not another AT-SPI2
technique. Not fixed in this pass -- flagged as a real, open,
architecturally-significant gap, not routed around. Investigated in
full afterward, live-checked findings and a real recommendation (the
`RemoteDesktop` portal's direct D-Bus methods, not raw `libei` FFI
bindings) written up in
[`m3-terminal-synthetic-input-proposal.md`](../architecture/m3-terminal-synthetic-input-proposal.md)
-- a proposal only, no code, no ADR written yet.

**Update (WP-56):** the proposal above was resolved into
[ADR-0047](../adr/0047-syntheticinputport-remotedesktop-portal-for-terminal-typing.md),
**Accepted** by the user with a load-bearing real-time indicator
condition, and then implemented -- `SyntheticInputPort`/
`PortalSyntheticInputAdapter`, the per-character fail-closed
focus-verification loop, the dedicated GSettings terminal profile
(visual half of the indicator, live-created and verified idempotent on
this real machine), and `SecretPort.set_secret` (the `restore_token`
write path, live-verified round-trip against this machine's real
gnome-keyring) are all real, gate-clean, and unit-tested against fakes.
**Genuinely not done, stated plainly rather than rounded up:** the
actual `RemoteDesktop.CreateSession`/`SelectDevices`/`Start` D-Bus
calls were never exercised against the real portal this pass --
deliberately, since the first real call pops a real, interactive OS
permission dialog needing the user physically present, explicitly out
of scope for this unattended pass (see `adapters/synthetic_input.py`'s
own module docstring for the full reasoning). This is the one real-D-Bus
adapter in this repo whose wire mechanics were not even manually
verified, unlike every other one -- the live-verification session is
where this closes: a real portal dialog, a real amber/red-bordered
terminal, a real spoken announcement, and a real typed command, all
watched by a physically-present human per ADR-0047's own design.

### Follow-up (2026-08-24): the VS Code and Brave findings above, re-investigated

A later, bounded pass re-opened exactly the two items above (no new
capability, no ADR) with two real, live-verified outcomes -- one a
genuine partial fix, one a full reversal of the earlier diagnosis.

**VS Code:** the fix above (`_atspi_read_text()` walks descendants,
bounded to 500 nodes, first-non-empty-wins) is implemented and is
correct on its own terms, but a live dump of VS Code's actual
accessible tree (`Atspi.get_desktop(0)` enumeration, full DFS) showed
the original diagnosis was wrong: the tree isn't deep, it's nearly
**empty** -- 2 reachable nodes total (`application`, `frame`), neither
exposing usable text. The real cause is that this machine's GNOME
accessibility bridge is off (`org.gnome.desktop.interface
toolkit-accessibility`, `org.gnome.desktop.a11y.applications
screen-reader-enabled`, and `org.a11y.Status.IsEnabled` all confirmed
`false` via live `gsettings`/`gdbus` queries) -- Chromium/Electron apps
(VS Code included) gate full AT-SPI2 tree publication behind this
toggle for performance, the same root cause already identified for the
Claude desktop app below. A per-process alternative
(`--force-renderer-accessibility`) was identified as a real candidate
but could not be verified live without fully quitting and relaunching
the user's actual, already-running VS Code window -- too disruptive to
do unattended, so it was not attempted. Enabling the bridge system-wide
would be exactly the kind of persistent, machine-wide change this pass
was told to avoid absent a narrow/reversible path. Net result: the
descendant-walk fix is real, committed, and a genuine improvement for
any app whose content sits below the root but *within* a published
tree -- it does not, by itself, close VS Code's gap, whose real fix is
a decision (accept the system-wide toggle, or scope
`--force-renderer-accessibility` into JARVIS's own VS Code launch path
and verify it against a fresh window) rather than a bounded code change.

**Brave:** re-diagnosed with the actual on-the-wire denial
(`journalctl`, not re-derived): `apparmor="DENIED" ... bus=
"accessibility" ... label="snap.brave.brave" ... peer_label=
"snap.code.code"`. The denying profile is **Brave's own** snap
confinement refusing to `receive` accessibility-bus messages from a
peer labeled `snap.code.code` -- not a restriction on the caller's
outgoing message, and not something `snap connections`/interface
wiring can fix (`snap interface accessibility` returns "no such
interface"; snapd has no such interface to connect on this system).
The decisive test: the same AT-SPI2 query, run via `systemd-run --user`
(a real, unconfined process -- confirmed via
`/proc/self/attr/current` reading `unconfined`, escaping this
session's own `snap.code.code` shell entirely) against the same,
already-running Brave instance, **succeeded** -- `get_child_count()`
returned `5`, zero AppArmor denials logged. This means the original
"still genuinely denied" finding above was correct only for queries
made *from this testing session's own confined shell*, not for
JARVIS's actual runtime: JARVIS is a plain, unpackaged Python process,
not itself snap-confined, and an unconfined peer is exactly what
Brave's profile does not deny. **No fix was needed and none was
applied** -- there is no real gap in JARVIS's own capability here, only
an artifact of testing through this particular tool's confined shell.
This is a genuine reversal of the earlier finding, not a new mitigation.

### A real, reproducible bug found and fixed: `focus()`/`is_focused()`/`is_visible_and_showing()` all checked the wrong AT-SPI2 node

The most significant finding of this pass. Exercising WP-56's own new
`is_focused()`/`is_visible_and_showing()` methods against a real
window for the first time (they shipped entirely untested against real
AT-SPI2 state) found: `focus()` genuinely failed, reproducibly, five
consecutive attempts, against a real, running `gnome-terminal` window
that was demonstrably visible and active on the real screen the whole
time. Root-caused, not guessed: a full AT-SPI2 tree dump found the
root `application` node (`find_or_launch`'s own handle target) has
**no** `Component` interface, **no** `Action` interface, and
`VISIBLE`/`SHOWING` both `False` -- always, regardless of the real
window's actual state -- while its `frame`-role child, one level down,
correctly reported a real, working `Component` interface and
`VISIBLE=True`/`SHOWING=True`/`ACTIVE=True`. A further, full tree dump
found the real focused widget (VTE's own `terminal`-role node,
`FOCUSED=True`) sitting seven levels deep, well past both the root and
its frame child.

This is the exact same category of bug `read_visible_text` already had
one confirmed instance of (the VS Code finding, post-M3) -- checking
only the top-level object was an unverified assumption baked into
`_atspi_focus` since WP-43 and copied into WP-56's new
`_atspi_is_focused`/`_atspi_is_visible_and_showing` without ever being
checked against a real window. **Fixed the same pass**: all three now
target a new `_find_frame_descendant()` helper's result (a bounded
walk for the first `frame`/`window`-role descendant) instead of the
root object directly; `is_focused()` additionally walks the full
subtree (focus can live arbitrarily deep, not just at the frame level)
matching `_find_focused_editable`'s own already-established pattern.
Re-verified live, same method, after the fix: `focus()` succeeded on
the first attempt, `is_visible_and_showing()` and `is_focused()` both
correctly returned `True` immediately afterward.

**Why this matters beyond a bug fix**: this bug sat directly inside
ADR-0047's own load-bearing safety mechanism -- had it shipped to the
live-verification session unfixed, `is_focused()` would have
structurally never returned `True` for a real `gnome-terminal` window,
meaning the very first per-character focus check in
`run_in_sandboxed_terminal`'s synthetic-typing loop would have aborted
immediately, before a single real character could ever be typed. This
would not have been unsafe (fail-closed correctly means no keystroke
fires when focus can't be verified) but would have made Terminal's new
capability completely non-functional the first time it was ever
exercised for real, for a reason having nothing to do with the actual
TOCTOU race ADR-0047 disclosed. Caught and fixed here instead, without
ever touching `SyntheticInputPort` or firing a real portal call.

No new automated test was added for this fix -- `_find_frame_descendant`
and the three corrected functions remain in this module's existing
"real, untested-by-design, proven by live verification" category
(same convention as every other real AT-SPI2 function here); this pass
*is* that live verification, the first one these three functions ever
got.

### What the structural meta-test actually proves, and what it genuinely cannot

Named plainly, matching this project's own "state real limits, don't
imply more than what was checked" discipline: the meta-test proves
that no real code path under M6b's own package boundary can call a
raw HTTP client, an unlisted `BrowserAutomationPort` method, or declare
a submission-shaped function parameter -- a real, mechanical guarantee
about *this codebase's own source text*, re-verified on every gate run.
**It cannot, and does not claim to, catch**:

- **A reasoning provider itself being coerced, via prompt injection or
  otherwise, into producing content that *describes* or *encodes* a
  submission action** (e.g. a drafted "cover letter" that is actually
  adversarial instructions aimed at some other, future system that
  might read it) -- the meta-test only inspects this repository's own
  Python source; it has no visibility into, and cannot constrain, what
  a cloud or local model *generates* as `Candidate.content`. The
  structural guarantee is that *this codebase* never submits anything
  regardless of what a provider outputs -- a real, different, and
  weaker (but still real) property than "no adversarial content can
  ever be generated."
- **A future dependency (a new third-party package) that reaches the
  network via a mechanism this ban-list does not name** -- the
  identifier ban-list is a fixed, named set (`requests`/`httpx`/
  `aiohttp`/`urlopen`/`urlretrieve`/`Request`/`post`), not an
  exhaustive enumeration of every possible way Python code can reach
  the network. A new library imported under a different top-level name
  that itself performs an HTTP POST internally would not be caught by
  identifier-scanning its *caller's* source alone.
- **Anything outside M6b's own scanned package path** -- if a future,
  unrelated capability elsewhere in this codebase were extended to
  accept a job-assistance `Candidate` and submit it somewhere, this
  meta-test would never see it; the boundary is scoped to
  `application/job_assistance/`, `kernel/job_assistance.py`,
  `ports/draft_storage.py`, and `adapters/draft_storage.py` only, by
  design (ADR-0058's own Decision names this exact scope).

None of this weakens ADR-0058's own real guarantee for what it actually
covers -- this codebase's own M6b code path genuinely has no submission
mechanism, mechanically re-verified, not merely documented. It is
named here so that guarantee is never overstated beyond what was
actually checked.

## Real, found gap: does ADR-0057's `Tier.CONFIRM` satisfy the charter? (2026-09-03)

Investigated directly, per the user's own explicit request, after
`jarvis send-email`/`jarvis create-calendar-event` were already
merged and CLI-invocable. Not assumed either direction; the real code
was read and quoted before drawing any conclusion.

**Question 1 -- can `Tier.CONFIRM` be satisfied by remote confirmation
alone, for these two capabilities specifically? Yes, confirmed
directly in code.** `domain/policy.py::evaluate()`:

```python
elif tier == Tier.CONFIRM:
    granted = context.physical_confirmation_available or context.remote_confirmation_available
```

versus `Tier.MANUAL_ONLY`, three lines above, which deliberately never
reads `remote_confirmation_available` even when `True`. `Effect.EGRESS_SENSITIVE`
(what `authorize_and_send_email`/`authorize_and_create_calendar_event`
declare for every non-`SECRET` invocation) floors at `Tier.CONFIRM`,
not `Tier.MANUAL_ONLY`, per `domain/capability.py`'s own
`_EFFECT_TIER_FLOOR`. Already directly, deliberately tested this way,
not merely inferable: `tests/property/test_communications_writer.py`'s
own `test_non_secret_email_bodies_are_never_denied_by_send_alone`/
`test_non_secret_attendee_bearing_summary_floors_at_confirm` both
assert `expected_granted = physical_confirmation_available or remote_confirmation_available`
against the real `EmailSendAuthorizer`/`CalendarEventAuthorizer` --
written and passing before this investigation, proving the behavior
being questioned was already deliberately built this way, not a bug.

**This is live today, not theoretical**: `jarvis send-email ...
--remote-confirmation-available` (no `--physical-confirmation-available`)
already authorizes a real SMTP send via the real CLI wiring merged
earlier the same day. `ManualConfirmationAdapter`
(`adapters/confirmation.py`) sharpens this further -- both booleans are
self-declared CLI flags with zero real presence/hardware verification
behind them today, by its own docstring's own admission ("Real
presence/hardware detection is future work"). "Remote confirmation"
currently means nothing more than a caller typing one flag.

**Question 2 -- did ADR-0057 or `m6a-communications.md` ever check
this reuse against the charter's own explicit language for email
specifically? No.** A direct search of both documents for
`physical`/`MANUAL`/`desktop`/`charter` found exactly one relevant
passage, in ADR-0057's own Consequences section -- and it treats the
question as speculative future policy, not a present requirement:
"if that distinction ever becomes real, necessary policy (e.g., a
future decision that email should require `MANUAL_ONLY` while
cloud-provider egress stays `CONFIRM`), it would need its own new
effect at that point." ADR-0057 named this exact possibility and
deferred it as an "if" -- without checking it against the project's
own founding charter, which names "sending emails" explicitly among
actions requiring "manual confirmation through the desktop interface,"
never voice/remote alone. That charter language is not currently
reproduced verbatim anywhere in this repo's own committed docs
(confirmed by direct grep across `CLAUDE.md` and `docs/`) -- it is the
system's own original, external founding description, referenced but
not quoted by `CLAUDE.md`'s own condensed "Destructive/irreversible/
credential actions always require `MANUAL_ONLY`" principle and by
ADR-0019's own Decision (whose own `Source` field is literally "CLAUDE.md
architecture summary, Milestone 0").

**`Effect.EGRESS_SENSITIVE` was calibrated for a different, narrower
risk.** ADR-0038's own Context: `EGRESS_SENSITIVE`/`EGRESS_SECRET`
were built for "M2's `ReasoningPort` adapters... the first
capabilities in this repo whose whole purpose is sending data to a
cloud provider" -- a cloud AI model seeing text, not a real, external
human receiving a real, unrecallable email or calendar invite.
ADR-0057 reused this floor by analogy to that narrower original
purpose (sound for the `SECRET`/`DENY` half -- an email can never
carry a `SECRET` value, matching cloud-egress's own zero-tolerance --
but never independently re-derived for the `CONFIRM`-tier,
remote-satisfiability question).

**ADR-0019's own real criteria is effect-based, not charter-text-based**:
"Any capability whose declared effects include DESTRUCTIVE, IRREVERSIBLE,
or CREDENTIAL is hard-pinned to `MANUAL_ONLY`." `Effect.EGRESS_SENSITIVE`
is not a member of that set. Two of the charter's own four named
examples ("deleting files," "changing passwords") map cleanly onto
this existing floor already; a third ("submitting applications") was
independently, directly resolved by the user as M6b's own *structural*
boundary (ADR-0058) -- stronger than `MANUAL_ONLY`, not weaker. The
fourth, "sending emails," is the one the charter names explicitly by
name, and it is the one this codebase currently classifies at
`Tier.CONFIRM`, remote-satisfiable.

**Conclusion: a real, evidenced gap existed.** Written up as
[`docs/adr/0059-email-and-attended-calendar-event-confirmation-tier-may-not-satisfy-the-charter.md`](../adr/0059-email-and-attended-calendar-event-confirmation-tier-may-not-satisfy-the-charter.md)
-- drafted Proposed, three real options laid out without a preference
baked in, matching this project's own established precedent of routing
decisions of this shape to the user directly rather than resolving
them remotely (ADR-0058's own "no auto-apply" boundary). No code was
changed as part of the investigation itself -- the finding was real
and live, but the fix was exactly the kind of first-principles
product-safety decision this project has consistently reserved for the
user. See "ADR-0059 Accepted, gap closed for real (2026-09-03)"
immediately below for what happened next.

### Equivalent mutants -- reasoned individually, not asserted by default

Every remaining survivor across all six target modules was read as a
real diff and reasoned about concretely; nothing was marked equivalent
without a specific, checkable argument:

- **Enum singleton identity** (`domain/policy.py`: `Eq_Is` on
  `tier == Tier.DENY`; `application/job_assistance/classification.py`:
  `Is_Eq` on `classification is Classification.SECRET`): `Tier` and
  `Classification` are `IntEnum`s -- Python guarantees enum members
  are singletons, so `is` and `==` are indistinguishable for any real
  comparison between two enum members, for every possible input.
- **Ordered-enum boundary comparisons** (`domain/policy.py`: `Eq_GtE`
  on `tier == Tier.DENY`, `Eq_LtE` on `tier == Tier.ALLOW`;
  `application/job_assistance/classification.py`: `Is_GtE` on
  `classification is Classification.SECRET`): `Tier.DENY` is the

  the maximum value in its own (`PUBLIC=0, PERSONAL=1, SENSITIVE=2,
  SECRET=3`) -- `>= <max>` can never diverge from `== <max>` since no
  larger value exists to compare against. `Eq_LtE` on
  `tier == Tier.ALLOW` sits in the final `elif` of an exhaustive
  tier-dispatch chain that has already excluded every tier above
  `ALLOW` (the minimum, `0`) by the time this branch is reached, so
  `<= Tier.ALLOW` and `== Tier.ALLOW` are likewise indistinguishable
  in the only reachable state.
- **Provably-impossible comparison direction**
  (`domain/policy.py`: `Gt_NotEq`/`Gt_IsNot` on
  `tier > invocation.descriptor.required_tier`): `effective_tier` is
  proven, by a separate, already-passing property test
  (`test_effective_tier_never_below_required`,
  `tests/property/test_capability.py`), to never fall below
  `required_tier` for any real invocation this codebase can construct
  -- given that domain invariant, `tier != required_tier` and
  `tier > required_tier` are mathematically identical (the `<` case
  the two operators would otherwise disagree on is unreachable), so
  the mutant is equivalent, not merely untested.
- **`TYPE_CHECKING`-guarded imports made unconditional**
  (`domain/policy.py`/`application/coding/classification.py`:
  `AddNot` on `if TYPE_CHECKING:`): both files declare
  `from __future__ import annotations` (PEP 563), so every type
  annotation in the module is stored as an unevaluated string, never
  executed as real code at runtime -- whether the guarded import
  actually runs or not has no observable runtime effect for any test,
  since nothing outside a type annotation ever refers to the
  conditionally-imported name.
- **`| None` return/parameter annotations, PEP 604 union syntax**
  (`application/coding/classification.py`: the `ReplaceBinaryOperator_BitOr_*`
  family, all 10 alternate binary operators, all three real `| None`
  call sites in the file): same PEP 563 root cause as the
  `TYPE_CHECKING` case above -- with lazy annotations active, the `|`
  in `tuple[str, ...] | None` is never compiled into a real binary
  operation at all, only stored as source text, so no operator
  substitution here (`+`, `-`, `&`, `^`, `<<`, `>>`, `%`, `*`, `/`,
  `//`, `**`) can ever produce an observable difference to any
  runtime test. Confirmed directly, not just inferred from the PEP:
  manually applying one such mutation by hand and running the exact
  test command reproduces a real `TypeError` only when the mutated
  expression is forced to evaluate outside its lazy-annotation
  context -- inside the annotation itself, under
  `from __future__ import annotations`, it never evaluates at all.
- **`@dataclass(frozen=True)` -> `frozen=False`**
  (`domain/policy.py`: `ReplaceTrueWithFalse` on `PolicyContext`):
  no test in this codebase ever attempts to mutate a constructed
  `PolicyContext` after creation, so relaxing immutability has no
  observable effect on any existing assertion. A real, narrow gap in
  principle (a future caller could accidentally mutate a `PolicyContext`
  in place and this test suite would not catch it), but out of this
  track's own scope -- it is a missing *negative* test for immutability
  itself, not a classification/policy-logic gap this track's own
  target list was scoped to close, so recorded here rather than
  silently fixed.

## Track 3 (property-matrix/fuzzing/concurrency pass): concurrency/thread-safety of the audit log, memory store, and capability registry (2026-09-04)

Real concurrent-access investigation of the four components this
pass's own instructions named: the capability registry, the audit log
writer, the memory store, and confirmation-chain storage (this
codebase's real "confirmation chain" *is* the audit chain -- `chain_path`/
`AuditChain`/`JsonFileAuditStorageAdapter` -- there is no separate
mechanism by that name, so these are one investigation, not two).

**A real, in-process race found in `domain/audit.py::AuditChain.append()`,
fixed for real, not just flagged.** A deterministic test (a real
`threading.Barrier`-free but `threading.Event`-forced interleaving, not
a timing-luck test) proved that two threads calling `.append()` on the
same `AuditChain` instance could both read the same pre-append
`sequence`/`previous_hash` state and both produce a record claiming
`sequence=0` -- a real, reproducible hash-chain corruption, the exact
"corrupted state" this pass's own instructions asked to check for.
Confirmed empirically before fixing, not assumed: the first version of
this test, run against the unfixed code, failed with
`assert [0, 0] == [0, 1]` -- both threads genuinely got sequence 0.
**Fixed** by adding a `threading.Lock` internal to each `AuditChain`
instance, held across the whole read-compute-append sequence in
`append()` -- a plain stdlib synchronization primitive, compatible
with `domain`'s own "no I/O, no async, no wall-clock/randomness"
purity constraint (verified: `lint-imports`'s C2 contract still
passes), no port/interface change. Two new tests in
`tests/unit/test_audit_concurrency.py`: a deterministic one proving a
second concurrent caller is genuinely blocked (not racing ahead) until
the first finishes, and a real, unforced 32-thread stress test proving
no natural OS scheduling ever produces a duplicate sequence either.

**A real, deliberately-unfixed cross-process gap, found and
documented, not silently patched.** A second real test
(`tests/unit/test_audit_storage_adapter.py::test_two_independent_writers_racing_on_the_same_file_silently_lose_one_writers_record`)
simulates two independent processes (two separate `AuditChain` +
`JsonFileAuditStorageAdapter` pairs, e.g. the CLI invoked twice
concurrently against the same `--chain-path`, or the CLI and a running
voice loop both targeting the same file) both loading the same
starting chain, both appending their own new decision, then saving in
sequence. Because `save()` always overwrites the whole file (already
documented in this adapter's own module docstring as "not handled
here: atomic writes... real robustness concern, out of scope"), the
second writer's save silently replaces the first's entirely -- the
first writer's own new audit record is not merged, not flagged as a
conflict, and is completely absent from the final file. **`verify()`
on the resulting chain still reports `valid=True`**: the surviving
chain is internally coherent, so this loss is invisible to the one
integrity mechanism this codebase currently has -- a real, concrete,
previously-undemonstrated instance of the adapter's own already-named
scope limitation, not a new discovery of the limitation itself.
**Deliberately not fixed in this pass**: closing it for real would
mean changing `AuditStoragePort`'s own `save()`/`load()` contract
(real file locking, or an append-only file format) -- a genuine
architecture decision, not a test-writing fix, and exactly the kind of
change `CLAUDE.md`'s own standing "never silently change the
architecture" rule exists to gate. Flagged here for the user's own
future decision, mirroring how the separate, still-queued
audit-log-integrity investigation is expected to surface a comparable
finding.

**`domain/registry.py::CapabilityRegistry.register()` has the same
class of check-then-act race in the abstract** (`if descriptor.id in
self._descriptors: raise ...` then `self._descriptors[descriptor.id] =
descriptor`), but investigated and confirmed **provably unreachable**
in this codebase's real call graph, not just unlikely: every single
`authorize_and_*` composition function across every `kernel/*.py`
module calls `build_default_registry()` fresh, per invocation --
grep-confirmed across all of `kernel/browser.py`, `communications.py`,
`desktop.py`, `files.py`, `memory.py`, `music.py`, `ping.py`,
`coding.py`. Each call constructs a brand-new `CapabilityRegistry`,
registers all 34 real capabilities into it synchronously and
single-threadedly within that one call, uses it, and lets it be
garbage collected -- there is no shared, long-lived registry instance
anywhere a second concurrent caller could ever race against. No lock
added: this is the "confirming single-writer correctness" outcome this
pass's own instructions explicitly allow for, backed by a structural
grep across the real codebase, not an assumption.

**`adapters/memory.py::SqliteMemoryAdapter` investigated and confirmed
fails closed by default, no fix needed.** `sqlite3.connect()` defaults
to `check_same_thread=True`; a real test
(`tests/unit/adapters/test_memory.py::test_using_the_same_adapter_from_a_second_thread_fails_closed_not_silently_corrupted`)

instance per process, never shared across threads by any real caller)

correct, sufficient mitigation here, not a reason to add custom
