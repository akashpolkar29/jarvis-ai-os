## The four systems, and why they stay separate

Stated explicitly, per this work package's own requirement:

- **`TaskStore`** (`jarvis.kernel.tasks`, via the real memory store) is
  the authoritative task state. A task's real status is always
  whatever is currently stored there -- never what an event claimed.
- **`EventBus`** (`jarvis.domain.events`) is a notification mechanism
  only. It observes real state changes after they happen; it never
  causes one, and losing an event (a missed poll, a bus nobody
  subscribed to) never loses real state, because the state was never
  *in* the bus to begin with.
- **The audit chain** (`jarvis.domain.audit.AuditChain`) remains the
  authoritative security/audit record, completely untouched by this
  work package. No event is ever written to it, and no audit record is
  ever derived from one -- investigated, not merged, per this work
  package's own explicit instruction. They solve different problems:
  the audit chain proves *what was authorized*; the event bus reports
  *what a task is currently doing*. Collapsing them would make every
  event carry audit weight it was never reviewed for, and would give
  the event bus an authority over the audit record it should never
  have.
- **The authorization kernel** (`AuthorizationOrchestrator`/
  `domain.policy.evaluate`) remains the sole authority over whether any
  action is permitted. Events cannot execute capabilities, grant
  authorization, approve a task, or change a `Tier` -- structurally:
  `EventBus.publish()` only ever calls a registered Python callable
  with an event *value*; nothing in this module's own API hands a
  subscriber a capability registry, an orchestrator, or any way to
  invoke one. The real flow remains
  `User -> Router -> Authorization -> Capability -> Task -> TaskStore -> Events -> UI`,
  never the reverse.

## Event model: exactly two real event types, not five

`jarvis.domain.events` defines `TaskCreated` and `TaskStatusChanged`.
The originating prompt's own conceptual sketch named five
(`TaskCreated`/`TaskStatusChanged`/`TaskCompleted`/`TaskFailed`/
`TaskCancelled`), then explicitly said not to implement every one
blindly if the real lifecycle doesn't support it. Investigated
directly: `jarvis.kernel.tasks` has exactly two real places stored
task state ever changes --
`write_task_record` (a brand-new record) and `update_task_status` (an
existing record's status, in place). The second of these already
carries real `previous_status`/`new_status`/`reason` fields able to
represent every real transition (`created -> running`,
`running -> completed`, `running -> failed`) without a separate class
per destination status -- `TaskCompleted`/`TaskFailed`/`TaskCancelled`
would just be `TaskStatusChanged` with `new_status` fixed to one
literal value each, real duplication for no real subscriber benefit.
`"cancelled"` remains a real, reserved value in
`jarvis.kernel.tasks.VALID_TASK_STATUSES` with no code path that
produces it yet (unchanged since WP-107) -- `TaskStatusChanged.new_status`
can already represent it the moment a real caller exists.

```python
@dataclass(frozen=True)
class TaskCreated:
    event_id: str
    task_id: str
    goal: str
    status: str  # usually "created"; see below for the one real exception
    timestamp: str


@dataclass(frozen=True)
class TaskStatusChanged:
    event_id: str
    task_id: str
    goal: str
    previous_status: str | None  # None only if no prior record could be read
    new_status: str
    reason: str | None
    timestamp: str
```

`event_id`/`timestamp` are never generated by `domain.events` itself --
`domain` may depend on the standard library only (C2), so it cannot
call a real `IdPort`/`ClockPort`. The real caller (`kernel.tasks`,
which already has both resolved) computes and passes them in, mirroring
`domain.audit.AuditChain.append`'s own `written_at` parameter exactly.

## Events are derived from real state changes, never fabricated

`write_task_record`/`update_task_status` publish their own event
**only after** the underlying `authorize_and_remember`/
`authorize_and_update` call was actually granted. A denied write
publishes nothing -- there is no real state change for an event to
describe. Proven directly, not assumed: `test_a_denied_task_creation_publishes_no_event_at_all`
and `test_a_denied_running_transition_publishes_no_status_changed_event`
(`tests/unit/test_tasks_kernel.py`) construct a real, denied
authorization and assert zero events were published.

`TaskStatusChanged.previous_status` is read from the real record
*before* it is overwritten (the same read `update_task_status` already
does for its own read-modify-write, not a second, separate guess) --
never independently re-derived or assumed.

## EventBus: synchronous, in-process, no concurrency

```python
bus = EventBus()
bus.subscribe(TaskCreated, my_handler)
bus.publish(TaskCreated(...))  # my_handler(event) called synchronously, right here
bus.unsubscribe(TaskCreated, my_handler)
```

Delivery is synchronous and deterministic: subscribers for one event's
exact type are called in the order they subscribed, and `publish()`
returns only once every subscriber has run. No background thread, no
async scheduling, no queue, no multiprocessing, no external broker
(Redis/Kafka/RabbitMQ/database-backed) -- all explicitly out of this
work package's own scope. There is deliberately no `EventBusPort`/
adapter split either: introducing a port for a mechanism with exactly
one real implementation and no second one even contemplated would be
speculative abstraction ahead of any real need.

**No lock**, unlike `AuditChain`'s own `threading.Lock` (added in
response to a real, demonstrated concurrent-access bug). Every real
caller in this codebase runs either fully synchronously in one thread
(every CLI subcommand) or inside `jarvis.cli.ui_server`'s own
deliberately single-threaded `http.server.HTTPServer` (WP-108), which
never hands two requests to two threads at once -- no real, concurrent
access to one `EventBus` instance exists anywhere today. Adding a lock
regardless would be exactly the speculative hardening this project's
own conventions reject; if a real concurrent caller is ever
introduced, add the lock then, the same way `AuditChain`'s own was.

## Subscriber failure semantics (a real, explicit decision)

A subscriber that raises is caught, logged via `logging.exception`
(visible, never silently swallowed), and:

- does **not** propagate to `publish()`'s own caller,
- does **not** stop delivery to the remaining subscribers.

The real state change a published event describes has, by
construction, already happened and already been durably persisted
*before* `publish()` is ever called -- a subscriber's own bug can
therefore never roll back or corrupt that state. Letting a subscriber
exception propagate and abort the real task-lifecycle operation's own
return value to its own, unrelated caller (e.g. `authorize_and_create_task`
failing because an unrelated logging subscriber had a bug) would be a
far worse coupling than logging and moving on. Proven directly:
`test_a_raising_subscriber_does_not_prevent_other_subscribers_from_being_notified`,
`test_a_raising_subscriber_does_not_propagate_to_publish_callers`,
`test_a_subscriber_failure_is_never_silently_swallowed`
(`tests/unit/test_events.py`).

## TaskStore integration: exactly two real hook points, `event_bus` is opt-in

`write_task_record`/`update_task_status`/`authorize_and_create_task`/
`authorize_and_run_task` all gained an optional `event_bus: EventBus | None = None`
parameter, resolved to a brand-new, empty `EventBus()` per call when
omitted -- exactly like `clock`/`id_port` already default. Publishing
to a bus nobody subscribed to is a real, harmless no-op, so **every
existing caller that never passes one behaves byte-for-byte as
before this change** -- proven directly by
`test_omitting_event_bus_is_a_harmless_no_op_matching_prior_behavior`.
`authorize_and_get_task`/`authorize_and_list_tasks` (pure reads) were
not touched at all -- they never change state, so there is nothing for
them to publish.

`jarvis.kernel.project` was **not** touched in this pass -- its own
`write_task_record` call sites simply never pass an `event_bus`,
defaulting to the same harmless no-op. A real, stated scope boundary,
not an oversight: `jarvis project start`/`status` events are not
observable via this work package's own wiring, consistent with not
making a drive-by change to that module's own already-delicate,
precisely-documented public contract.

## `kernel.router.authorize_and_route`: one real hook, one real gap stated honestly

`authorize_and_route` gained the identical `event_bus` parameter,
passed straight through to `authorize_and_create_task` -- a
`COMPLEX_GOAL` route's own `TaskCreated` event is genuinely published
in-process the moment `jarvis ui` creates a task.

**The real, honest limitation**: the router never runs a task (a
`COMPLEX_GOAL` route creates, never runs -- WP-104's own unchanged,
explicit design), so no real `TaskStatusChanged` event can ever
originate from `authorize_and_route` today. Only
`kernel.tasks.authorize_and_run_task` (a separate, explicit call --
today, only `jarvis task run <id> <goal>`, a different CLI invocation
and therefore a different process with its own, separate `EventBus`
instance) can ever produce one. `jarvis.cli.ui_server`'s own
`GET /api/tasks/<task_id>` endpoint does not depend on this at all --
see below.

## UI event delivery: polling, not SSE -- and why

`jarvis.cli.ui_server.JarvisUiServer` owns one real, shared `EventBus`
for its whole lifetime, passed into every `authorize_and_route` call,
with two minimal, real subscribers attached at construction
(`_log_task_created`/`_log_task_status_changed`, each a real
`logging.info` call) -- the one, deliberately small "future adapters"
consumer this pass actually builds, proving the wiring is real rather
than inert plumbing nothing uses.

This server does **not** use Server-Sent Events, long-lived streaming,
or WebSockets for live task updates. The reason is structural, not a
preference: WP-108 already committed this server to
`http.server.HTTPServer` (single-threaded, by deliberate design --
see `docs/architecture/wp108-ui-foundation.md`). An SSE connection
that stays open indefinitely would block that one real thread from
handling *any* other request -- including the very status-recovery
query described below -- for as long as it stayed open, directly
contradicting that already-committed design.

Instead: `GET /api/tasks/<task_id>` does one real, authoritative read
of the real, persistent task store
(`kernel.tasks.authorize_and_get_task`) per call, with **no
`EventBus` involvement at all**. The frontend (`ui_static/index.html`)
polls this endpoint every 2 seconds, for up to 60 attempts (~2
minutes), appending one new, real message to the conversation each
time the task's own real status actually changes, and stopping once a
real terminal status (`completed`/`failed`/`cancelled`) is reached, a
real fetch failure occurs, or the attempt ceiling is hit. It never
fabricates progress -- an unchanged status between polls produces no
new message at all, and there is no percentage or synthetic
"streaming" of any kind.

## Reconnection / status recovery

Because `GET /api/tasks/<task_id>` always re-reads the real,
authoritative task store directly, it solves browser reconnection for
free, with no new mechanism: a refreshed or disconnected-then-
reconnected browser has nothing but this same real query to ask again,
and gets the real, current answer back regardless of what it missed
while disconnected. This also covers the cross-process case named
above honestly: if a task is later run via a separate `jarvis task run`
invocation (a different process, a different, short-lived `EventBus`
instance this server's own bus was never told about), `GET /api/tasks/<task_id>`
still correctly reports that real, cross-process status change,
because the real task store is shared even though the in-process event
bus is not. Proven directly:
`test_get_task_status_recovers_a_real_task_created_outside_this_http_request`
creates a task via a direct kernel call the running server never saw,
then confirms a real `GET` correctly recovers it.

No persistent event history/database was introduced, per this work
package's own explicit instruction -- events are ephemeral; the task
store remains the one, authoritative source of truth.

## Security / authorization -- unchanged

`127.0.0.1`-only binding, single-threaded server, no new capability,
no new `Effect`/`Tier`, no localhost-as-physical-confirmation
inference, ADR-0058 (no automated job-application submission) and
ADR-0062 (per-step authorization, no batch pre-approval) both
completely untouched -- `kernel/router.py`'s and
`application/planning/`'s own real authorization logic was not
modified anywhere in this work package, only given one additional,
optional, purely-observational parameter.
